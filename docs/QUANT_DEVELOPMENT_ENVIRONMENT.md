# COMMON quantitative development environment
## Implemented in the development branch
- Project-relative text file paths, a monospace source editor, four previous revisions, restore, export and deletion. Python source is stored as text, not executed. No remote file system.
- Daily CSV import, SMA crossover candidate grid, up to 60 valid parameter pairs, fixed rolling train/test windows, and training-only parameter selection by Sharpe. Each out-of-sample block is disjoint; simulated positions carry between folds. Flat transaction costs; buy-and-hold benchmark.
- Browser Web Worker with 60-second timeout and cancellation for validation. This is an isolated computation thread, not a sandbox for arbitrary code.
- Separate performance, fold, parameter grid, regime, trade log and reproducibility views. SHA-256 identifies the uploaded text; it does not establish authenticity or licensing. The original CSV is not retained.
- Regime classification from the trailing 20 observed daily returns ending two bars before the evaluated return. Threshold: 25% annualized volatility. Descriptive conditional mean returns, not regime forecasts. Position changes record simulated preceding close and signal date, not brokerage orders.
- Browser-local storage, max five validation reports per project; export/delete to make room. No financial or user credentials stored in these files. Storage is subject to browser quota.

## Structured notebook increment
Project notebooks provide ordered notes, dataset profiles, return distributions, drawdown analyses, SMA backtests and executable Python cells. Dataset analyses retain source fingerprints. For **QUANT-061**, add a Python code cell, save the source, then select **Run Python cell** to review that exact source and consent to execution and package downloads. Each run starts in a fresh instance of the browser runtime described below. Variables are scoped to the current run, and each tab allows one active Python run across its notebook and Python lab. **Stop execution** ends the current run.

Each Python cell retains its latest success, failure or cancellation, with text output, truncation indicator, runtime version, package selection and timestamp. Source and output are saved in browser-local workspace storage and included in the explicit notebook export. Editing inputs invalidates prior output. A result from an edited or deleted cell is discarded. Persistent kernels, project data injection, shared notebook storage and remote compute remain outstanding.

## Experimental Python lab
An opt-in Pyodide 0.27.7 browser runtime runs user-reviewed Python in a fresh sandboxed iframe without same-origin access and a disposable blob worker. The iframe CSP blocks normal application network destinations and permits the pinned CDN runtime path. Only explicitly entered source and allowlisted scientific package names are sent to the worker; no authenticated data, datasets, provider keys or banking services are passed in. Output is capped, execution times out and can be stopped. This is local experimental compute, not a hardened cloud sandbox: untrusted code, secrets and large jobs are prohibited; CDN requests are possible and browser memory limits are not guaranteed. Verify real runtime loading, cancellation, output, and isolation in browsers before claiming production readiness. Reference: https://pyodide.org/en/0.27.7/usage/downloading-and-deploying.html

### Browser Python environment manifests

For **QUANT-069**, the Python lab and notebook code cells show pinned package versions before consent. Each run records its Pyodide and CPython versions, target architecture, the upstream release lockfile URL and SHA-256, and the requested packages and complete transitive dependency closure from that lockfile. Package pins include version, SHA-256 and dependency names. Open **Environment manifest** in a saved run to view the versions. **Export run** and **Export notebook** include the machine-readable manifest. Earlier runs remain readable without inferred package metadata.

A manifest identifies the environment COMMON requested before running the user's code. The preparation flag records whether the runtime reached execution after loading the selected packages. The hashes identify released artifacts. COMMON does not independently rehash network responses at execution time or attest to dependency changes made by user code. The manifest applies to the browser workspace.
## Treasury revisions observed in this browser

Open **Markets → Macro & Rates → Treasury revision comparison** and refresh the source over time. The terminal retains the two most recent distinct successful windows per series, up to 120 debt and 72 T-bill rate observations per window. The observations are public data saved locally in this browser. An identical response updates the check timestamp and preserves the earlier comparison. A failed or invalid refresh retains the last valid retrieval for the affected series and labels it accordingly.

The comparison matches Treasury record dates and computes exact decimal changes in dollars or percentage points. It counts dates that enter or leave a rolling window separately from changed values. Each window includes the browser retrieval time and a SHA-256 fingerprint of the source query and normalized observations when secure browser hashing is available. An observed difference is evidence that this browser received two values for one record date. It does not establish the provider's publication time, an official correction notice, or historical availability before capture. Complete point-in-time vintage storage and shared ingestion remain open.

### Constrained portfolio allocation

**QUANT-169, QUANT-170, QUANT-179.** Open **Portfolio laboratory → Optimization**, select two to eight historical CSV datasets and enter current scenario weights. You can copy the invested weights of the simulated ledger when the selected datasets have distinct symbol labels covering every simulated holding. Copying excludes cash. Optimization supports the minimum-variance objective and minimum variance subject to a historical annual-return floor. Shared minimum and maximum weights apply per asset, and target weights are long-only and sum to 100%.

The optimizer uses simple returns whose start and end dates match across all selected assets, with at least 30 matched intervals. It prefers a declared adjusted close, uses an arithmetic mean and sample covariance with the sample-size-minus-one denominator, and annualizes at 252 intervals. Users can apply 20% diagonal shrinkage. Both covariance estimates add one millionth of average asset variance to every diagonal entry to stabilize singular samples. It solves the convex quadratic program over the feasible weight bounds in a browser worker. The frontier contains the minimum-volatility portfolio and up to six additional feasible portfolios spaced by sample return through the maximum feasible sample return.

The saved report records the engine version, model choices, covariance matrix, input file fingerprints, price bases, omitted interval counts, date range, current weights and frontier. Comparing a point shows hypothetical weight changes and one-way turnover, calculated as half the sum of absolute weight changes. The same data estimates and compares the allocations. The report provides no out-of-sample or execution result. Borrowing, liquidity, taxes and transaction costs are outside the model. Save up to ten reports locally and export them as JSON.
