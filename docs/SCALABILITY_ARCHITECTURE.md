# COMMON — scalability architecture and engineering gates

Status: target architecture and acceptance plan; capacity is unmeasured. Not a claim of production readiness or an authorization to purchase or deploy infrastructure.

## Baseline risks
- The authenticated community client periodically refreshes broad queries every 25 seconds, including fixed-size result sets (e.g. 200 discussions). Replace with scoped incremental queries, cursor pagination and authorized realtime invalidation. Do not increase global limits as a scaling strategy.
- Browser-local projects, notebook runs and datasets are bounded and not cross-device durable. IndexedDB dataset listing currently reads entire records to extract metadata. Separate metadata from blobs; persist eligible cloud data by owner/project with object storage and explicit quotas.
- FastAPI's development default is SQLite; the old prototype auth and Supabase member identity are separate. Production must use one authoritative identity and managed PostgreSQL, migrations, connection pooling and stateless APIs. Do not use ephemeral SQLite for real members or finance.
- Browser Python and current quant tools reduce initial hosting expense but are bounded, not hardened multi-tenant remote execution. Model gateway is gated; long-lived agents, distributed jobs, storage and cost controls are unfinished.
- Current community tables have basic feed/member/message indexes. Verify query plans for actual RLS-filtered queries, rather than assuming those indexes prove scale.

## Target topology
Web/mobile clients -> CDN/static assets -> authenticated API boundary -> modular domain services (identity, community, social, governance, research, portfolio, market data, notifications) -> PostgreSQL primary + private object storage. Add independently scalable worker pools for ingestion, quantitative jobs, AI orchestration, notifications and media. Keep financial execution and accounting isolated behind explicit authority, provider and reconciliation controls. Use a modular monolith first for normal domain APIs, independently deployed compute workers where necessary. Extract services only when measured load, isolation or team needs justify it. Avoid premature Kubernetes, sharding and paid dependencies.

## Mandatory implementation contracts
1. Stateless API requests, centralized identity, per-resource authorization, stable versioned contracts, bounded request/response sizes, explicit timeouts and connection pools. No in-memory-only durable jobs or state.
2. PostgreSQL indexes driven by EXPLAIN (ANALYZE, BUFFERS) in disposable fixtures; composite indexes for membership and stable feed/message cursors; avoid N+1, unbounded SELECT *, global polling and full-table scans. Keyset pagination with stable timestamp/id tie-break and correct authorization. Read replicas or partitioning only when justified; never use stale reads for money authorization.
3. Social timelines: initially fan-out on read using indexed visibility/follow filters and cursors; hybrid fan-out for high-volume workloads if measured. Private membership changes revoke future access, cache entries, subscriptions and attachment grants. Realtime channels scoped to eligible members; reconnect/backoff, deduplicated event IDs and cursor catch-up. Background-tab subscriptions/polling should pause or reduce frequency.
4. Jobs: durable queue interface with database-backed implementation where economical, atomic claim/lease, heartbeat, bounded retries with jitter, idempotency key, dead-letter/reconciliation, cancellation, per-user/circle concurrency caps and global backpressure. Transactional outbox for state-change events. Do not run arbitrary user code in the API or database process.
5. Compute: dedicated isolated runtime per job/project as appropriate, resource and wall-clock limits, ephemeral filesystem, no host credentials, deny-by-default network, approved input artifacts, output validation, cleanup and per-tenant usage accounting. Separate AI orchestration from heavy numerical workers. Allow queued jobs and fair scheduling; degraded capacity must not take down community browsing.
6. Market data: provider-neutral adapters, batched ingestion, caching, deduplication, canonical instrument/time keys, as-of timestamps, provenance, entitlements, rate limits, stale indicators. Use partitioned/time-series or columnar/object storage only when measured data volume requires it; never duplicate the same market series per user. Never cache private financial data in public/CDN caches.
7. Financial operations: isolate accounting/execution permissions and credentials, exact minor units, immutable balanced journals, idempotent verified provider events, transactional invariants, reconciliation, independent approvals, append-only audit, no double-spend under retries or concurrent requests. Financial correctness is mandatory at every load level. No live activation until legal and partner gates.
8. Operations: metrics for p50/p95/p99 latency, errors, request volume, DB CPU/connections/slow queries, queue age/depth, job completion and cancellation, realtime lag, AI token/cost, storage and egress. Structured logs and correlation IDs without secrets or sensitive research/finance payloads. Explicit budget caps, alarms, rate limits, graceful degradation, documented backups and restore drills. Staging separation, backwards-compatible migrations, feature flags, controlled releases and rollback.

## Capacity targets and validation (proposed, not observed)
Test staged user populations (1k, 10k, 100k registered accounts) independently of active users; test 50, 250 and 1,000 concurrent synthetic sessions, with increasing traffic only as cost and environment permit. Define a realistic read/write mix and dataset sizes. Large-scale tests require infrastructure and owner-approved budgets; use small disposable local fixtures for free development. Never load-test production, live financial providers or paid model APIs without authorization. Measure actual sustainable requests/sec, resource saturation, queue wait and cost; do not infer capacity from account count. Use k6 or Locust and PostgreSQL query plans, plus integration and failure-recovery tests.
Initial proposed SLO targets for normal browsing: p95 <= 500ms for warm scoped API reads under agreed load, <1% unexpected server errors, realtime delivery p95 <= 2s under agreed load (excluding reconnect), no lost committed writes. Long-running research gets separate queue/start/completion metrics, not a universal latency promise. Specify region, fixture size, request mix and measurement window. Financial invariants must pass regardless of load. Review targets against actual product requirements and affordable hosting.

## Rollout decisions
Development: existing repo, local fixtures, free-tier limits, browser research where appropriate.
Pilot: persistent cloud identity/data, pagination and indexed queries, abuse controls, constrained jobs, monitored limits, tested backups, approved private beta.
Growth: horizontally scaled API/workers, tuned database, shared caching where safe, durable jobs and queues, CDN/object storage, realtime capacity management.
Large-scale: measured bottleneck-specific replicas, partitioning, service extraction or regional delivery, operational staff and budgets. No fixed user-number capacity guarantee.

## Acceptance
Workstream 01 owns API contracts, topology, pagination, identity and integration performance; 02/03 own AI and compute limits; 04 owns ingestion/data scaling; 05 owns bounded quantitative algorithms; 06–08 own feed/chat/realtime behavior; 09 owns transactional finance correctness; 10 owns load tests, observability, security, budgets and release gates. PRs must identify scaling impact, query patterns, resource bounds, testing evidence and remaining limits. Do not mark scale-ready until tests and operational verification are recorded.
